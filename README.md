# splitbrain

A minimal Raft consensus implementation in Go — a 3-node distributed key-value store with leader election, log replication, and a real-time web dashboard.

## Overview

**splitbrain** demonstrates the core ideas of the [Raft consensus algorithm](https://raft.github.io()):

- **Leader election** — nodes hold randomized election timeouts; if no heartbeat arrives, a candidate requests votes and wins with a majority
- **Log replication** — the leader appends entries to its log and replicates them to followers before committing
- **Quorum writes** — a write is committed only after `⌊n/2⌋ + 1` nodes acknowledge it
- **Automatic recovery** — a rejoining node catches up its log from the leader's heartbeats

The cluster is intentionally kept small (3 nodes) and in-memory to make the behavior easy to observe and experiment with.

## Getting Started

```bash
# Build and start the cluster + dashboard server
./start.sh
```

Then open the dashboard in your browser:

```
http://localhost:8080/dash
```

> Accessing `http://localhost:8080` redirects automatically to `/dash`.

The services start on:

| Service   | Address                       |
|-----------|-------------------------------|
| alpha     | http://localhost:8001         |
| beta      | http://localhost:8002         |
| gamma     | http://localhost:8003         |
| dashboard | http://localhost:8080/dash    |

To stop the cluster:

```bash
./stop.sh
```

## HTTP API

Each node exposes the same API:

| Method | Endpoint          | Description                        |
|--------|-------------------|------------------------------------|
| POST   | `/write`          | Write a key (leader only)          |
| GET    | `/read?key=<k>`   | Read a key from local store        |
| GET    | `/status`         | Node state, term, log, store       |
| GET    | `/health`         | Liveness check                     |
| POST   | `/vote`           | Raft vote RPC (internal)           |
| POST   | `/append-entries` | Raft append-entries RPC (internal) |

### Write example

```bash
curl -s -X POST http://localhost:8001/write \
  -H 'Content-Type: application/json' \
  -d '{"key":"user:1","value":"Alice","operation":"SET"}'
```

If the target node is not the leader, the response will contain `"error":"not_leader"` — redirect the request to the current leader.

### Read example

```bash
curl -s http://localhost:8001/read?key=user:1
```

### Status example

```bash
curl -s http://localhost:8001/status | python3 -m json.tool
```

## Node Control

Use `node-control.sh` to manage individual nodes during experiments:

```bash
# Kill node 2 (simulates a crash)
./node-control.sh kill 2

# Restart node 2
./node-control.sh start 2

# Check the state of all nodes
./node-control.sh status

# Tail logs for node 1
./node-control.sh logs 1
```

Node numbers map to: `1 = alpha`, `2 = beta`, `3 = gamma`.

## Dashboard

Open `dashboard/index.html` directly in a browser — no server required. It polls each node every second and shows:

- **Node cards** — role (LEADER / FOLLOWER / OFFLINE), term, log size, commit index, uptime, and the current key-value store contents
- **Topology view** — SVG diagram with live state and term for each node
- **Operation panel** — send SET / DELETE writes to any node or auto-route to the leader
- **Event log** — timestamped feed of all actions and results
- **Scenario buttons** — one-click experiments (see below)

## Scenarios

The dashboard includes four built-in scenarios for exploring Raft behaviour:

| Scenario | What happens |
|---|---|
| **Write Flood** | Sends 20 rapid writes and shows replication in real time |
| **Kill Leader** | Identifies the current leader and prints the kill command; watch the remaining nodes elect a new leader within ~2 s |
| **Partition** | Identifies a follower, guides you through killing it, writing data, then restarting it; the rejoining node syncs its log automatically |
| **Split Brain** | Kills 2 of 3 nodes; the sole surviving node cannot reach quorum so writes are rejected — demonstrating the CP guarantee of CAP theorem |

## Configuration

Nodes are configured via environment variables:

| Variable  | Default              | Description                          |
|-----------|----------------------|--------------------------------------|
| `PORT`    | `8001`               | HTTP listen port                     |
| `NODE_ID` | `node-<PORT>`        | Human-readable node name             |
| `PEERS`   | `[]`                 | JSON array of `host:port` peer addresses |

Example — running a fourth node manually:

```bash
PORT=8004 NODE_ID="delta" \
  PEERS='["localhost:8001","localhost:8002","localhost:8003"]' \
  ./bin/dbnode
```

## How Raft Works (brief)

```
Followers  ──── timeout ────►  Candidate  ──── majority votes ────►  Leader
   ▲                                                                     │
   └──────────────────── heartbeat (AppendEntries) ◄────────────────────┘
```

1. All nodes start as **followers** and reset an election timer on each heartbeat.
2. If the timer expires, a follower becomes a **candidate**, increments its term, and requests votes from peers.
3. A node grants its vote if the candidate's log is at least as up-to-date as its own and it hasn't voted this term.
4. A candidate with votes from a majority becomes the **leader** and starts sending heartbeats.
5. Client writes go to the leader, which appends the entry to its log, replicates it, and commits once a majority acknowledges.
6. Committed entries are applied to the in-memory key-value store on each node.

## Limitations

This is an educational implementation, not production-ready:

- State is **in-memory only** — all data is lost on restart
- No **log compaction** or snapshots
- No **membership changes** (fixed 3-node cluster)
- No **client retry / redirect** logic built into the API
- No TLS or authentication
